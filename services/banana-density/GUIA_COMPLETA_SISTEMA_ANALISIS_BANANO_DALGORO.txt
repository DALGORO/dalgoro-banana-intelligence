================================================================================
0. PROPÓSITO DE ESTA GUÍA
================================================================================

Esta guía explica, desde cero y paso a paso, cómo construir un sistema que:

1. Recibe una ortofoto georreferenciada de una finca bananera.
2. Recibe el límite de análisis mediante coordenadas almacenadas en Excel.
3. Valida que la imagen y el límite sean técnicamente utilizables.
4. Recorta la ortofoto sin modificar el archivo original.
5. Divide el recorte en imágenes pequeñas o tiles con solape.
6. Ejecuta un modelo YOLO para detectar plantas de banano.
7. Convierte las detecciones desde píxeles a coordenadas reales.
8. Elimina detecciones duplicadas causadas por el solape de los tiles.
9. Genera un inventario espacial en CSV y GeoPackage.
10. Calcula superficie, cantidad de plantas y densidad observada.
11. Analiza espaciamientos, vecinos próximos y patrón espacial.
12. Genera densidad por hexágonos.
13. Identifica oportunidades geométricas de inspección o posible siembra.
14. Excluye vías, canales, infraestructura y zonas no cultivables.
15. Prioriza candidatos para la inspección técnica.
16. Genera superficies continuas de densidad KDE.
17. Produce seis mapas corporativos.
18. Produce un informe técnico PDF con identidad gráfica DALGORO.
19. Guarda estados, logs y manifiestos para poder reanudar una ejecución.
20. Permite operar todo mediante una interfaz gráfica amigable.
21. Permite auditar posteriormente que una ejecución esté completa.

Esta guía no convierte automáticamente un espacio abierto en una planta faltante.
Los productos “oportunidad geométrica” y “candidato de siembra” son elementos
para verificación técnica en campo. Una vía, canal, drenaje, sombra, edificio,
borde o planta no detectada puede producir un espacio aparente.

================================================================================
1. PRINCIPIOS DE DISEÑO
================================================================================

1.1. NO MODIFICAR LOS DATOS ORIGINALES

La ortofoto, el Excel, el modelo y las capas originales se leen sin alterarlos.
Cada ejecución crea su propia carpeta y sus propios resultados.

1.2. UNA CARPETA POR EJECUCIÓN

Cada análisis se almacena con nombre y fecha:

    NOMBRE_FINCA_AAAAMMDD_HHMMSS

Ejemplo:

    FINCA_BUENAVISTA_20260718_202736

1.3. PROCESAMIENTO POR ETAPAS

Cada etapa recibe productos de la etapa anterior y genera productos verificables.
Si una etapa falla, las etapas terminadas se conservan.

1.4. CONFIGURACIÓN SEPARADA DEL CÓDIGO

Los parámetros técnicos deben estar en YAML. El código Python no debe contener
rutas de una finca específica.

1.5. TRAZABILIDAD

Cada etapa debe guardar como mínimo:

- Fecha de inicio.
- Fecha de finalización.
- Parámetros utilizados.
- Rutas de entrada.
- Rutas de salida.
- Estado success/false o COMPLETADO/ERROR.
- Advertencias.
- Errores.
- Tiempo de ejecución.

1.6. ESCRITURAS ATÓMICAS

Los JSON, YAML, CSV, GeoPackage y raster finales deben escribirse primero con un
nombre temporal y luego reemplazarse. Esto reduce archivos incompletos cuando
hay un corte de energía o una interrupción.

1.7. RESULTADOS GIS INDEPENDIENTES DE QGIS

QGIS puede utilizarse para revisar los productos, pero no es obligatorio para
ejecutar el sistema. El procesamiento se realiza con Python, Rasterio,
GeoPandas, Shapely, Pyogrio, NumPy, SciPy, OpenCV, Ultralytics y ReportLab.

4. REQUISITOS DE HARDWARE
================================================================================

4.1. CONFIGURACIÓN MÍNIMA

- Windows 10 u 11 de 64 bits.
- Procesador de cuatro núcleos o superior.
- 16 GB de memoria RAM.
- 20 GB libres para instalación y pruebas pequeñas.
- Más espacio libre según el tamaño de ortofotos y cantidad de fincas.
- Pantalla con resolución mínima 1366 x 768.

4.2. CONFIGURACIÓN RECOMENDADA

- Procesador de ocho núcleos o superior.
- 32 GB de memoria RAM.
- Unidad SSD.
- Al menos 100 GB libres para proyectos, tiles y resultados.
- GPU NVIDIA compatible con PyTorch, opcional.

4.3. CPU O GPU

El sistema puede funcionar en CPU. La inferencia será más lenta.

Cuando exista GPU NVIDIA:
- Instalar controlador NVIDIA.
- Instalar una versión de PyTorch compatible con el controlador y CUDA.
- Validar con torch.cuda.is_available().
- No instalar paquetes CUDA al azar.

================================================================================
8. DATOS DE ENTRADA
================================================================================

8.1. ORTOFOTO

Formato:
- .tif o .tiff
- GeoTIFF.
- CRS definido.
- Transformación geográfica válida.
- Preferentemente sistema proyectado en metros.
- Bandas RGB.
- Resolución suficiente para distinguir plantas.

No convertir una imagen JPG común en “ortofoto” solamente cambiando la
extensión. La georreferenciación debe ser real.

8.2. EXCEL DEL LÍMITE

Formato:
- .xls o .xlsx.

Columnas recomendadas:

    ORDEN    X          Y           EPSG
    1        612345.10  9634567.20  32717
    2        612400.30  9634570.80  32717
    3        612410.20  9634490.10  32717
    4        612340.50  9634480.50  32717
    5        612345.10  9634567.20  32717

Reglas:
- X y Y deben ser números.
- EPSG debe corresponder a la ortofoto.
- ORDEN define la secuencia del polígono.
- El primer y último punto pueden ser iguales.
- Si no son iguales, el sistema debe cerrar el polígono.
- No debe existir autointersección.
- El límite debe intersectar la ortofoto.

8.3. MODELO YOLO

Formato:
- best.pt

Ubicación recomendada:

    F:\PROY_CONTEO_BANANO_1\
    runs\detect\banano_v3\weights\best.pt

8.4. EXCLUSIONES OPCIONALES

Formato:
- GeoPackage .gpkg.
- Geometrías poligonales.
- CRS compatible o transformable al CRS del inventario.

Ejemplos:
- Vías.
- Canales.
- Drenajes.
- Bodegas.
- Viviendas.
- Estaciones de bombeo.
- Áreas sin cultivo.
- Infraestructura.

La versión de la interfaz debe detectar las capas espaciales. Cuando haya varias,
debe combinarlas en una capa persistente llamada:

    exclusiones

No debe enviarse al geoprocesamiento el texto:

    COMBINAR TODAS LAS CAPAS

Ese texto es solamente un marcador de interfaz.

Los valores de coordenadas y dimensiones están normalizados entre 0 y 1.

9.2. data.yaml

Propósito:
Definir el dataset para Ultralytics.

Contenido recomendado:

    path: F:/PROY_CONTEO_BANANO_1/dataset_banano
    train: images/train
    val: images/val
    test: images/test

    nc: 1

    names:
      0: banano

Verificar:
- Las rutas deben existir.
- La clase usada en todos los TXT debe ser 0.
- No debe haber imagen sin etiqueta, salvo negativos intencionales.
- No debe haber TXT sin imagen.

9.3. organizar_dataset.py

Propósito:
- Recibir imágenes y etiquetas.
- Comprobar correspondencia de nombres.
- Separar train y val.
- Copiar, no destruir, los archivos originales.
- Utilizar semilla fija para reproducibilidad.

Contenido funcional mínimo:

- Constantes de carpetas.
- Función que localiza imágenes.
- Función que verifica el TXT asociado.
- Función de división train/val.
- Función de copia segura.
- Resumen final con cantidades.
- Bloque if __name__ == "__main__".

No debe mezclar imágenes de validación dentro de entrenamiento después de haber
reportado las métricas finales.

9.4. auto_etiquetar.py

Propósito:
Generar etiquetas iniciales usando un modelo previo.

Contenido funcional mínimo:

- Carga de YOLO.
- Recorrido de imágenes.
- Predicción con umbral de confianza.
- Conversión a formato YOLO.
- Escritura de TXT.
- Opción para no sobrescribir etiquetas revisadas.
- Registro de imágenes sin detecciones.

Las etiquetas automáticas deben revisarse manualmente. No deben considerarse
verdad de campo sin control visual.

9.5. entrenar_v3.py

Propósito:
Entrenar el detector final.

Estructura recomendada:

    from ultralytics import YOLO
    from pathlib import Path

    DATA_YAML = Path("data.yaml")
    BASE_MODEL = Path("yolov8s.pt")

    def main():
        model = YOLO(str(BASE_MODEL))
        model.train(
            data=str(DATA_YAML),
            epochs=...,
            imgsz=640,
            batch=...,
            project="runs/detect",
            name="banano_v3",
            patience=...,
            workers=...,
            device="cpu" o "0",
        )

    if __name__ == "__main__":
        main()

Productos:

    runs\detect\banano_v3\
    +-- args.yaml
    +-- results.csv
    +-- results.png
    +-- confusion_matrix.png
    +-- BoxP_curve.png
    +-- BoxR_curve.png
    +-- BoxPR_curve.png
    +-- weights\
        +-- best.pt
        +-- last.pt

Usar best.pt para producción.

9.6. conteo_coordenadas.py

Es un componente legado que puede:
- Ejecutar conteo directo.
- Convertir detecciones a coordenadas.
- Servir como referencia histórica.

No debe modificarse para integrar el sistema nuevo. El sistema automatizado
utiliza módulos independientes y un orquestador.

21. ERRORES CONOCIDOS Y SOLUCIÓN
================================================================================

21.1. YOLO INDICA QUE NO EXISTEN TILES

Causa:
El sistema envía 02_tiles, pero los archivos están en 02_tiles\geotiff.

Solución:
pipeline_orchestrator.py debe utilizar find_tiles_directory() y enviar:

    02_tiles\geotiff

a YOLO y georreferenciación.

21.2. KeyError: branding

Causa:
cartography.yaml o report.yaml versión 1.

Solución:
Usar version: 2 y comprobar:

    cartography.branding
    report.branding

21.3. Layer 'COMBINAR TODAS LAS CAPAS' could not be opened

Causa:
La interfaz guardó el marcador como nombre real.

Solución:
- Utilizar interfaz R4 o posterior.
- Reparar la ejecución.
- La configuración final debe contener:

    exclusions_layer: exclusiones

21.4. HUELLA CRÍTICA DIFERENTE

Causa:
Se cambió la configuración después de iniciar el run.

Solución:
- No editar manualmente configuracion_analisis.yaml.
- Crear un nuevo run cuando cambie ortofoto, modelo o densidad.
- Solo utilizar el reparador cuando la corrección sea controlada.

21.5. CARPETA DE SALIDA YA EXISTE

Causa:
Los módulos evitan sobrescritura.

Solución:
- Crear nueva carpeta.
- Utilizar --force-stage para archivar la salida anterior.

21.6. ESPACIO INSUFICIENTE

Solución:
- Eliminar únicamente ejecuciones de prueba respaldadas.
- No eliminar best.pt.
- No eliminar una ejecución activa.
- Conservar PDF, GIS, configuración, estado y logs del proyecto entregado.

21.7. CUDA FALSE

No es un error. El sistema funciona en CPU.

21.8. GPKG SIN CAPAS ESPACIALES

Revisar gpkg_contents. Las tablas de atributos no pueden utilizarse como
geometrías de exclusión.

8. Todos los escenarios de una misma entrega deben usar la misma densidad.

10. El informe debe indicar sus limitaciones.

27. CONCLUSIÓN
================================================================================

El sistema está compuesto por módulos pequeños y verificables. La clave para
mantenerlo estable es conservar la separación entre:

- Entrenamiento.
- Configuración.
- Procesamiento.
- Presentación.
- Control.
- Auditoría.

La interfaz facilita el uso, pero el núcleo técnico continúa siendo main.py,
pipeline_orchestrator.py y los módulos de banana_analyzer. Una ejecución nunca
debe considerarse válida únicamente porque generó archivos: debe completarse el
pipeline, revisar los manifiestos, abrir los mapas, abrir el PDF y ejecutar la
auditoría final.
